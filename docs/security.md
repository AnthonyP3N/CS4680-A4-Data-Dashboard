# AskData security model

AskData lets a language model write SQL against someone's data. The model is
treated as untrusted: nothing it writes runs until code, not another model,
has checked it. The same goes for the data itself, uploaded files and anything
saved earlier. This page lists what is protected, how, and where the tests are.

## What is protected, and how

| Safeguard | How | Tests |
|---|---|---|
| No SQL runs without validation | Every statement goes through `agent/validator.py` (sqlglot) before it reaches a database: first answers, self-corrections, re-runs of saved queries, and confirmed changes (checked again at commit) | `test_agent.py`, `test_security.py::test_a_change_is_checked_again_just_before_it_is_applied` |
| Dangerous statements are always refused | DROP, ALTER, CREATE, PRAGMA, ATTACH, VACUUM, SELECT INTO, transactions, multiple statements; system tables (`sqlite_*`, `pg_*`, `pragma_*`, `information_schema`); file, extension, sleep and memory-bomb functions (`load_extension`, `readfile`, `pg_read_file`, `randomblob`, ...) | `test_security.py::test_unsafe_sql_is_refused_even_with_changes_allowed`, `test_datasources.py` (every dialect) |
| Reads can't write | Reads run on a SQLite connection opened in `mode=ro`; even SQL that skipped the validator fails | `test_security.py::test_read_connection_is_physically_read_only` |
| Changes need explicit confirmation | INSERT/UPDATE/DELETE only with **Allow data changes** on; then a dry run in a rolled-back transaction, a preview, and a confirm button | `test_ui.py`, `test_chat.py` |
| No whole-table changes | UPDATE and DELETE need a WHERE clause that mentions a column (`WHERE 1 = 1` is refused) | `test_security.py` |
| Row count re-checked | At commit the affected rows must equal the preview's count, or the change is rolled back | `test_security.py::test_a_change_with_a_different_row_count_than_its_preview_is_not_applied` |
| Query duration and size limits | A progress handler stops queries after `ASKDATA_QUERY_TIMEOUT_S` (default 8 s); rows are capped by `ASKDATA_MAX_ROWS` (default 1,000) twice, by LIMIT and at fetch; no single text value may exceed 10 MB; cells over 1,000 characters are cut | `test_security.py::test_query_limits_come_from_settings_within_bounds`, `test_a_query_cannot_build_a_huge_value` |
| Question limits | Per workspace (10 a minute, 300 a day), per network address (20 a minute), and app-wide for the app's own key (60 a minute); shared by every session in the process | `test_security.py` (limits section) |
| Sensitive columns | Their values are never sent to the model (schema samples and listed values are replaced), answers that read them are not saved, and their values are masked in results | `test_security.py` (masking section), `test_storage.py`, `test_memory.py` |
| Workspace isolation | Every storage query is scoped to a workspace that belongs to an owner; a guessed id returns nothing; each workspace has its own data files | `test_security.py::test_another_owner_cannot_open_change_export_or_delete_anything`, `test_storage.py` |
| Memory never crosses workspaces | Retrieval reads only the current workspace's memories, and only for the current data source or workspace-wide ones | `test_memory.py`, `test_security.py` |
| API keys are never stored | Visitors' keys live only in session memory; anything shaped like a key is masked before storing or logging | `test_storage.py::test_pasted_api_key_is_not_stored`, `test_ui.py` |
| Logs don't hold result data | The activity log records counts, SQL, timings and decisions, never result rows; masked columns are named, not their values | `test_security.py::test_answers_hide_sensitive_values_everywhere_they_go` |
| Prompt injection | Data is fenced as data in the prompt (rule 10); sample values are cut to 80 characters on one line, so they can't start a new prompt section; uploaded names are rebuilt from a strict character set; and whatever the model is talked into, the validator still decides | `test_security.py` (prompt injection section) |
| Generated answers are labelled | The chat and every export (JSON, Markdown, HTML) say answers are generated by an AI model | `test_security.py::test_answers_and_exports_are_labelled_as_generated` |
| Audit trail | Every question, model response, validation, execution, masking, block, rate limit and commit is logged with a request id | `test_security.py::test_every_safety_decision_is_in_the_audit_trail` |
| Custom model endpoints can't reach private networks | https only, every resolved address must be public, no redirects | `test_llm.py` |

## Masking sensitive values

A data source's owner marks columns as sensitive in the Data tab and chooses how
their values appear in results:

| Mode | Example | Use |
|---|---|---|
| Partly hidden (default) | `m•••@example.com`, `M••• M•••`, `••••77` | Enough to tell rows apart |
| Fully hidden | `••••` | Screen sharing, demos |
| Shown as stored | `maya.martinez1@example.com` | The owner decides the values aren't private here |

Masking is decided from the SQL, not from column names. `agent/masking.py` uses
sqlglot's column lineage to trace every output column back to the table columns
it was computed from, through aliases, joins, subqueries, CTEs, UNIONs and
`SELECT *`. If any of those is sensitive, the output column is masked, so
`UPPER(email) AS contact` is caught and `products.name` isn't confused with
`customers.name`. COUNT is the one exception. If the SQL can't be traced, every
text column is masked.

Masking happens once, straight after the query runs, so the table, chart, CSV
download and any copy kept later all get the masked values. The preview of rows
a change will touch and the Data tab's table preview are masked by column.

## Known limits

* **Inference through filters.** Masking hides values that are returned, not what a
  filter reveals: `SELECT COUNT(*) FROM customers WHERE email LIKE 'a%'` still
  answers a question about emails. Marking a column sensitive also tells the model
  not to use it, but that is guidance, not enforcement. If a column must never be
  queried at all, leave it out of the data you connect.
* **Default filters and ownership rules are guidance.** They're sent to the model as
  rules, and the validator doesn't enforce them. Row-level security belongs in the
  database.
* **Limits are per process.** Question counts are kept in memory, so they reset when
  the app restarts and aren't shared between several servers. The per-address limit
  depends on Streamlit seeing the visitor's address, which some proxies hide.
* **Error messages go back to the model.** When a query fails, the database's error
  message is sent to the model so it can correct the SQL. SQLite's messages name
  tables and columns, not values; other databases may differ.
* **Private links are bearer tokens.** Anyone who has a link has that workspace. Use
  `ASKDATA_AUTH = "login"` when that isn't acceptable.
* **The operator can see everything.** Whoever runs the server can read its disk and
  memory, including visitors' keys while a session is open.
